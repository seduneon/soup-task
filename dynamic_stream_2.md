# Как работает динамический стриминг в Soup

Динамический стриминг в D2 выбирает, где держать веса слоёв и какие активации сохранить для обратного прохода. Он делает выбор один раз перед обучением, используя замеры прошлых запусков и число предстоящих обновлений оптимизатора. Цель — сократить время всего запуска с учётом подготовки кэшей.

## Что можно разместить в памяти

В обычном режиме замороженные веса слоёв читаются с SSD и через RAM попадают в рабочие буферы GPU. Когда буфер освобождается, его использует следующий слой. Повторный проход снова запрашивает веса, которых уже нет в буфере.

| Вариант | Что экономит | Чем платим |
| --- | --- | --- |
| Оставить веса части слоёв в VRAM | Чтение с SSD и передачу RAM → GPU при повторном обращении | VRAM и время на начальную загрузку |
| Оставить веса других слоёв в RAM | Повторное чтение с SSD. Передача RAM → GPU сохраняется | RAM и время на заполнение кэша |
| Сохранить активации последних слоёв в VRAM | Повторный forward этих слоёв при backward | VRAM до момента обратного прохода |

Сначала подбираются резидентные слои GPU, затем RAM-кэш заполняется другими слоями. Остальные веса продолжают подгружаться с SSD. Если разрешено сохранение активаций, оно проверяется с уже установленными кэшами весов и делит с ними бюджет VRAM.

## Как записывается профиль

В режиме `record` сначала запускают обычный стриминг с нулевыми кэшами и пересчётом активаций. Затем отдельно запускают интересующие варианты с тем же стартовым чекпоинтом, данными и параметрами обучения. Каждый такой запуск делает два прогревочных и шесть измеряемых обновлений. Все восемь обновлений обучают адаптер.

В общий JSON записываются фактические индексы слоёв в RAM и GPU, число слоёв с сохранёнными активациями, время подготовки и среднее время обновления после прогрева. При расчёте времени подготовки отдельно учитывается надбавка первых двух шагов. Профиль привязан к модели и индексу весов, данным, конфигурации обучения, GPU и драйверу, лимитам RAM и версиям реализации. Длину обучения можно менять при повторном использовании профиля.

## Как выбирается план

1. В режиме `reuse` тренер берёт фактическое число обновлений оптимизатора `N` и загружает подходящий профиль. Если нет свежего профиля с замером обычного стриминга, работает обычный режим.
2. Из замеренных вариантов остаются те, которые укладываются в заданные потолки RAM и GPU. Варианты с сохранением активаций рассматриваются при `stream_recompute: auto`.
3. Для каждого варианта прогнозируется время всего запуска по формуле ниже. Из времени подготовки вычитаются только пробы, которые нужны для записи профиля. Стоимость свежей проверки выбранного варианта остаётся в оценке.

   ```text
   Время запуска = подготовка − пробы только при записи + N × время обновления
   ```

4. Побеждает вариант с минимальным прогнозом, если его время строго меньше 98% от прогноза обычного стриминга. Затем тренер проверяет, что тот же план помещается в текущую память. Для GPU выполняется свежий forward/backward с рабочей формой батча, с запасом под оптимизатор. RAM-кэш пересчитывается по текущей доступной памяти и лимитам контейнера. Если выбрано сохранение активаций, проверяется именно записанное число последних слоёв.
5. Если проба отклоняет план или из-за памяти меняется состав слоёв, тренер возвращается к обычному стримингу. Просроченный профиль (старше 30 дней), несовпадение конфигурации и возобновление с чекпоинта тоже ведут к обычному режиму. После выбора план применяется на весь запуск.

Например, обычный режим требует 12 секунд подготовки и 9 секунд на обновление. Вариант с кэшем требует 30 секунд подготовки и 8,5 секунды на обновление. За 18 обновлений обычный режим быстрее (174 против 183 секунд). За 100 обновлений кэш окупается (880 против 912 секунд) и проходит порог выигрыша, если всё ещё влезает в память.

## Как включить

Фрагмент для dense SFT на одной CUDA-карте с дисковым стримингом. Это запись обычного режима в профиль.

```yaml
training:
  stream_layers: true
  stream_source: disk
  stream_cache_profile: ./cache-profile.json
  stream_cache_profile_mode: record
  stream_ram_cache_mb: 0
  stream_resident_layers: 0
  stream_recompute: "on"
```

Для записи вариантов меняют лимиты кэшей и при необходимости ставят `stream_recompute: auto`. Затем переключают режим на `reuse`, указывают допустимые потолки и запускают обучение. `stream_resident_layers: auto` разрешает использовать число GPU-слоёв из профиля. Для сохранения активаций нужны AdamW и `fast_lora: false`.

Текущий профиль в PR #5 рассчитан на стандартный dense-стример Transformers SFT с фиксированным размером батча. Сочетания с L2L и `per_expert` пока вне его области. В проекте DeepSeek `l2l_auto_k` подбирает число микробатчей, чьи активации помещаются в RAM.
